## 聚焦鲁棒性探针

2026-08-05 对一次性配置继承包执行了额外的短提示、多文件修复探针。基线有 3 个失败测试：浅层嵌套覆盖会丢失父配置同级字段；调用方可通过修改返回缓存污染后续调用；`extends` 循环会引发 `RecursionError`。Agent 在 3 轮内达到 `verified_ok`，只修改两个实现模块，3 个项目测试全部通过。保存在工作区之外的评测器代码随后通过了更深检查，包括三层继承、递归字典合并、列表替换、源数据不可变、缓存隔离、基础配置稳定性和缺失键行为。

同一轮加固还增加了以下离线回归：提供商 HTTP 404 后的有界模型恢复；子进程超时时的 bytes 类型部分输出；损坏的项目记忆和反思记录；重要代码标识符位于长提示后部；终端聊天/编码/修复路由。这些测试在修复前暴露了 3 个通用运行时缺陷；`coding_agent/` 中没有加入任何探针或夹具名称。

2026-08-02 还在外部验收代码位于目标工作区之外的情况下，运行了两个额外一次性项目：

- 一个从零生成的可安装 Python CLI 产生 10 个项目文件和 52 个通过的项目测试。外部验收构建 wheel、安装到独立虚拟环境，同时执行 `python -m` 和 PEP 621 控制台命令，并通过 7 个隐藏行为检查：标准 CSV 引号、重复类别、空输入、无效值和表头。
- 一个预置多文件修复以 4 个失败项目测试开始。Agent 只修改解析器和聚合器，报告 `verified_ok`，保留项目测试，并通过 6 个隐藏检查，包括单次迭代器、物理行号、无效名称和畸形记录。

从零实现最初暴露了一个保守假阴性：生成的控制台命令没有安装在 Agent 环境中，因此被正确拒绝为未知可执行文件。运行时随后被通用化，只适配当前项目标准 `[project.scripts]` 表中声明的命令。重新验证执行全部 5 个计划步骤，通过 24 个必需原子，并生成干净的 `verified_ok` 最终门禁。核心运行时没有加入任何夹具或项目名称。

## 提示详细程度与项目规模矩阵

2026-08-02 的第二个一次性矩阵使用简短和详细提示，覆盖小型修复、中型从零项目和更大的可安装 CLI。验收程序保存在生成工作区之外。

- 两个小型解析器修复都达到 `verified_ok`；简短契约通过 11 个隐藏检查，详细契约通过 15 个。重复单位、排序和非字符串错误语义只对详细提示强制，因为简短提示没有指定。
- 两个中型文本处理项目都在反馈修复后达到 `verified_ok`，各通过 10 个隐藏检查，包括在独立虚拟环境构建与安装 wheel。
- 简短大型项目最初暴露了修复目标锁定和推测范围缺陷。通用运行时修复后，全新运行在 7 个工具轮次达到 `verified_ok`，通过全部 8 个需求原子，构建并安装 wheel，并通过 14 个隐藏检查。
- 详细大型项目通过 45 个项目测试和 14 个隐藏检查。修复审计发现不需要实现变更；只有直接执行证据通过每个必需原子时，最终门禁才会接受这种无操作结果。

矩阵还暴露并修复了一个无界产物证据验证循环（手动停止前重复 175 条验证记录）、持久化图状态中缺少检查点标志、把修复误判为仅验证的离线回退，以及模块入口状态传播问题。核心包不包含任何矩阵夹具名称或分支。

## 真实仓库修复试点

当前试点通过 Agent 运行后的隐藏验收解决 4/4 个固定历史缺陷，并且没有修改受保护测试源码。3 个局部案例与 Agent 最终门禁成功一致。新增的多文件 Cookiecutter 案例通过外部验收，但因为 Agent 没有构造足够的直接执行证据，仍是保守最终门禁假阴性。其中一个局部案例含有额外隐藏兼容性检查，捕获并消除了最初过宽的修复。协议、各案例结果、通用修复和样本限制见 [REAL_WORLD_EVALUATION.zh-CN.md](REAL_WORLD_EVALUATION.zh-CN.md)。

v2 脱敏摘要将外部验收与 Agent 成功声明分开。该试点包含 3 个真阳性声明、0 个假阳性声明、1 个假阴性声明、47 次模型调用和 431,051 个报告 Token。一个验收通过的修复修改了 3 个实现文件，只能作为第一个多文件数据点，不能代表广泛多文件基准能力。
